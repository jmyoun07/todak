## 1. '우리 데이터로만 답하게 하려면' — 지금 무엇이 있고 무엇이 없는가

### 1-1. 핵심 판정 세 줄

1. **의학 내용 자체는 이미 충분히 있습니다.** 다만 챗봇이 읽을 수 없는 곳(화면 HTML 파일)에 들어 있습니다.
2. **담을 그릇이 없습니다.** 데이터베이스에 지식 저장용 표가 하나도 없고, 챗봇 함수에는 '찾아보는 단계' 자체가 없습니다. 지금 챗봇의 답변 본문은 전부 모델의 기억에서 나옵니다.
3. **안전장치는 이미 규칙으로 강제되고 있습니다.** 응급·위기 배너는 모델이 무슨 말을 하든 코드가 붙입니다.

### 2-3. 이용조건이 서로 충돌 — 서면 확인이 반드시 필요합니다

**식약처 공공데이터의 '임의 가공 금지' 문구 문제입니다.**

- 공공데이터포털 쪽 표기: 이용허락범위 **"제한 없음"**
- 식약처 자체 안내(의약품안전나라 공공데이터 개요) 기본원칙: **"출처 표시, 내용에 대한 임의 가공 금지"**

두 문구가 정면으로 다릅니다. 토닥은 허가사항의 딱딱한 문장을 40~70대 환자용 쉬운 말로 바꿔 보여주려 하는데, **그것이 바로 '가공'**입니다. "제한 없음"이면 가능하고, "임의 가공 금지"면 원문 병기 또는 원문 그대로 노출만 가능합니다. 이 한 줄이 챗봇 답변 설계 전체를 좌우합니다.

- **판정: 확인 필요.** 된다고 단정하면 안 됩니다.
- **해야 할 일:** 식약처 데이터 담당에 "허가사항 원문을 환자용 평이한 문장으로 재작성해 제공해도 되는지"를 한 문장으로 질의하고, 회신(또는 무응답 기록)을 IRB 문서철에 남기는 것입니다. *메일 발송은 교수님 승인 후에 진행하겠습니다.*
- **회신 전까지의 안전한 설계:** 쉬운 말 요약 + 접기 영역에 허가사항 원문 그대로 병기 + 출처·조회일자 표시.

## 3. 설계안

### 3-1. 검색 단계를 어떻게 넣을 것인가

현재 구조는 `질문 → 규칙 문구 → 외부 모델 → 답변`입니다. 여기에 한 단계를 끼웁니다.

`질문 → **우리 DB에서 관련 조각 찾기** → 찾은 조각만 모델에게 주며 "이 범위 안에서만 답하라" → 답변 → **규칙 배너 강제 부착(기존 그대로)**`

구체적인 방법은 새로 만들지 않습니다. 이미 있는 두 자산을 옮깁니다.

| 단계 | 방법 | 근거 |
|---|---|---|
| 그릇 만들기 | 지식 테이블 신설. 권한 설정은 기존 설정 테이블의 "모두 읽기 가능 + 연구팀만 쓰기" 패턴을 복제 | 새 권한 설계 불필요 |
| 내용 채우기 | 화면 HTML 22종을 [왜 생겨요 / 이렇게 관리해요 / 음식 / 이럴 땐 병원에] 섹션 단위로 잘라 넣기 | 22개 화면이 동일 구조라 기계적으로 잘립니다 |
| 찾기 | 프로토타입의 검색 로직(키워드 + 글자 두 개씩 겹침 비교 + 치료유형 가중) 이식 | 벡터·임베딩 없이 동작합니다 |
| 주입 | 프로토타입의 "참고 지식 안에서만 답하세요" 프롬프트 이식 | 검색 0건일 때 문구까지 이미 있습니다 |
| 안전 | 기존 정규식 배너 57개는 **그대로 둡니다** | 검색 성공 여부와 무관하게 붙습니다 |
