# 환자 확인 서류(진단서·소견서 사진) — 수파베이스 설정과 확인 방법

2026-09-28 · 토닥 가입 단계에 **‘환자 확인 서류’ 화면(99)** 이 새로 들어갔습니다.
02 약관 동의 → **99 서류 사진 올리기** → 03 기본 정보 순서입니다. 앱은 글자를 읽지 않고(OCR 없음) 사진만 받으며, 토닥 담당자가 대시보드에서 나중에 눈으로 확인합니다.

> 아래 1번(SQL 실행)을 하기 전까지 앱은 이 단계를 **건너뜁니다.** 지금 쓰고 계신 분도, 새로 가입하시는 분도 막히지 않습니다.
> SQL 을 실행한 뒤부터 새로 가입하시는 분만 99 화면을 지납니다.

## 1. SQL Editor 에 붙여넣기 (한 번만)

1. 수파베이스 대시보드 → 왼쪽 **SQL Editor** → **New query**
2. `C:\Users\rudtn\todak-app\supabase\sql\2026-09-28_patient_verify.sql` 파일 내용을 **통째로** 붙여넣고 **Run**
3. 맨 아래 결과 표가 이렇게 나오면 끝입니다.

| 항목 | 결과 |
|---|---|
| 1) 확인 기록 표 | 있음 ✓ |
| 2) 표 보안(RLS) | 켜짐 ✓ |
| 3) 표 규칙 | insert own verification · read own verification |
| 4) 사진 보관함 verify-docs | 있음 · 비공개 ✓ |
| 5) 보관함 규칙 (2개여야 해요) | 2개 ✓ |
| 6) 보관함을 가리지 않는 다른 규칙 (0 이어야 안전) | 0개 ✓ |

- 여러 번 실행해도 괜찮습니다(있는 것은 건너뛰거나 같은 내용으로 다시 만듭니다).
- **5)가 ‘0개 ✗’** 로 나오면, 프로젝트 설정상 SQL 로 보관함 규칙을 만들 권한이 없는 경우입니다. 아래 ‘대시보드에서 규칙 만들기’로 두 개를 만들어 주세요.
- **6)이 0개가 아니면**, 예전에 다른 기능 때문에 ‘모든 보관함에 두루 통하는’ 규칙을 만든 적이 있다는 뜻입니다. 그 규칙이 있으면 서류 사진도 함께 열릴 수 있으니, **Storage → Policies** 에서 그 규칙이 무엇인지 확인해 주세요. (지금 토닥 앱은 서류 사진 말고는 Storage 를 쓰지 않습니다.)

### 대시보드에서 규칙 만들기 (5)가 ‘0개’일 때만)

**Storage → Policies → verify-docs 옆 New policy → For full customization** 으로 두 개를 만듭니다.

| 이름 | 허용 동작 | 대상(Target roles) | 조건 |
|---|---|---|---|
| `verify-docs: upload own folder` | INSERT | authenticated | `bucket_id = 'verify-docs' and (storage.foldername(name))[1] = auth.uid()::text` |
| `verify-docs: read own folder` | SELECT | authenticated | `bucket_id = 'verify-docs' and (storage.foldername(name))[1] = auth.uid()::text` |

UPDATE·DELETE 규칙과 anon(로그인 안 한 사람) 규칙은 **만들지 않습니다.** 환자분은 자기 폴더에 올리고 자기 것만 볼 수 있고, 고치거나 지우는 것은 담당자만 합니다.

> 보관함 규칙이 빠진 채(5)가 ‘0개’) 그대로 두시면, 새로 가입하시는 분은 99 화면에서 사진이 올라가지 않습니다.
> 이때 앱은 “지금은 사진을 받을 준비가 덜 됐어요”와 함께 **‘가입 먼저 이어 하기’** 단추를 보여 드려 가입이 막히지는 않게 했습니다(그분은 나중에 내 정보에서 올리시게 됩니다). 그래도 SQL 실행 직후 5)번을 꼭 확인해 주세요.

## 2. 토닥 담당자가 확인하는 방법

### 사진 보기
1. **Table Editor → patient_verifications** — `status` 가 `pending`(확인 중)인 줄이 새로 올라온 서류입니다. `user_id` 와 `file_path` 를 봅니다.
2. **Storage → verify-docs → (그 user_id 이름의 폴더)** → 사진 파일을 누르면 오른쪽에 미리보기가 뜹니다.
3. 누구의 서류인지 이름·이메일과 함께 보시려면 SQL Editor 에서 SQL 파일 맨 아래 ‘담당자용’ 첫 번째 조회문(`-- ` 를 지우고)을 실행하시면 됩니다.

### 결과 적기
- Table Editor 에서 그 줄의 `status` 칸을 두 번 눌러 바꿉니다.
  - `approved` = 확인 완료
  - `rejected` = 다시 올려 주세요 — 이때 `note` 칸에 **환자분께 보일 한 줄**을 쉬운 말로 적어 주세요.
    예: `글씨가 흐려요. 밝은 곳에서 다시 찍어 주세요.` / `유방암이 적힌 서류로 다시 올려 주세요.`
- `reviewed_at`(확인한 시각)은 `status` 를 바꾸면 자동으로 적힙니다.
- 환자분은 앱 **내 정보 › 환자 확인 서류** 에서 `올리지 않음 · 확인 중 · 확인 완료 · 다시 올려 주세요` 로 보십니다. ‘다시 올려 주세요’면 `note` 가 그대로 보이고, 그 자리에서 새 사진을 올리실 수 있습니다(새 줄이 하나 더 생기고, 가장 최근 줄이 지금 상태가 됩니다).

### 확인 뒤에는 사진을 꼭 지워 주세요
- 앱의 동의 안내에 **“확인을 마치면 사진은 지체 없이 복구할 수 없는 방법으로 파기”** 한다고 적었습니다. 확인하신 뒤에는 **Storage → verify-docs → 그 사진 선택 → Delete** 로 지워 주세요.
- 표의 줄(`status`·`file_path`·날짜)은 확인 기록으로 남겨 두시면 됩니다. 사진만 지웁니다.
- SQL 로 `storage.objects` 줄을 직접 지우는 것은 권하지 않습니다(수파베이스가 막아 둔 프로젝트도 있고, 줄만 지워지고 실제 파일이 남을 수 있습니다). Storage 화면에서 지워 주세요.
- **주민등록번호 뒷자리가 보이는 사진**은 확인 여부와 상관없이 **바로 지우고**, `rejected` + `note` 에 `주민등록번호 뒷자리가 보여서 사진을 지웠어요. 가리고 다시 찍어 주세요.` 처럼 적어 주세요.
- 계정 삭제 요청을 처리하실 때: 표의 줄은 계정과 함께 지워지지만(외래키 cascade), **Storage 의 사진은 저절로 지워지지 않습니다.** verify-docs 안의 그 사람 폴더도 함께 지워 주세요.
- 사진을 PC 로 내려받지 않는 것을 권합니다. 내려받으셨다면 확인 뒤 지워 주세요.

## 3. 무료 플랜 저장 용량 어림

- 앱이 올리기 전에 휴대폰에서 **긴 변 1600px · JPEG(품질 0.85)** 로 줄입니다. 종이 서류 사진은 한 장에 대략 **0.2~0.8MB** 입니다(시험용 진단서 그림은 50KB).
- 무료 플랜 파일 저장 공간은 **1GB** 입니다. 참여자 100명이 한두 장씩 올려도 **약 50~150MB**(10% 안팎)이고, 확인 뒤 지우시면 거의 남지 않습니다.
- 보관함 한 장 상한은 10MB 로 걸어 두었습니다(앱이 줄여 올리므로 넘을 일은 거의 없습니다).

## 4. IRB · 개인정보 관련 확인하실 것

1. **민감정보(건강정보)입니다.** 진단서·소견서에는 병명·진단일·성함이 함께 있어 개인정보보호법상 민감정보(제23조)에 해당합니다. 앱은 99 화면에서 **(필수) 진단서·소견서 사진 수집·이용 동의**를 **받는 그 자리에서 따로** 받고(항목·목적·보유기간·거부 시 불이익 안내 포함), 동의문 버전 `pv1 2026-09-28` 을 줄마다 함께 남깁니다.
2. **주민등록번호는 받지 않습니다.** 주민등록번호는 고유식별정보라 법적 근거 없이 모을 수 없습니다(제24조의2). 화면에서 찍기 전에 **뒷자리 7자리를 가리시라고** 크게 알리고, 미리보기에서 한 번 더 확인하시게 합니다. 그래도 보이는 사진이 오면 위 2번대로 바로 지워 주세요.
3. **사진 속 위치정보(GPS)·기기 정보는 올라가지 않습니다.** 앱이 사진을 휴대폰에서 다시 그려 올리므로 EXIF 정보가 빠집니다(크롬 엔진에서 GPS 가 든 시험 사진으로 확인함 · 실제 아이폰·안드로이드 기기 확인은 아직).
4. **연구계획서·동의서 변경 여부.** ‘진단서 사진’은 새로 모으는 항목입니다. IRB 승인 동의서·연구계획서에 이 항목이 없다면, **실제 참여자에게 켜기 전에 IRB 변경심의가 필요한지** 확인해 주세요. SQL 을 실행하지 않으면 앱에서 이 단계는 꺼진 채로 있습니다.
5. **약관(25) 화면의 민감정보 항목에 ‘환자 확인 서류 사진’을 넣었습니다** — 민감정보 동의 탭의 처리 항목·안내, 개인정보 처리방침 2번(모으는 정보)·4번(보관·파기)에 `(2026-09-28 추가)` 표시와 함께 적었습니다.
   - 다만 **동의문 버전(DOC_VERSION v6)과 시행일(2026-09-18)은 올리지 않았습니다.** 앱은 가장 최근 동의 기록의 버전이 앱의 버전과 **정확히 같아야** 통과시키므로, 버전을 올리면 **이미 가입하신 모든 분이 로그인할 때 02 약관 동의로 다시 끌려갑니다.** 이 사진은 99 화면에서 받는 자리 동의로 따로 받기 때문에 전원 재동의는 하지 않았습니다.
   - 처리방침 본문에 “바뀌는 내용은 시행일 7일 전부터 알린다”는 문장이 있습니다. 정식 개정으로 처리하시려면 시행일·버전을 올리되, 전원 재동의를 원하지 않으시면 재동의 판정 방식을 먼저 바꿔야 합니다(개발 쪽에 말씀해 주세요).
6. **이미 가입하신 분(오늘 아침까지 가입)은 막지 않습니다.** 기본 정보(치료 단계)까지 마치신 분은 로그인해도 99 로 가지 않고, **내 정보 › 환자 확인 서류** 줄에서 ‘올리지 않음’을 보시고 원하실 때 올리실 수 있습니다. 필요하시면 기존 참여자께는 앱 밖에서 따로 부탁드려 주세요.
7. ‘다시 올려 주세요(rejected)’가 된 분도 앱 사용은 막히지 않습니다(내 정보에서 빨간 글씨로 보입니다). 막아야 한다면 개발 쪽에 말씀해 주세요.
